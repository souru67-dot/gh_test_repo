## 1. 開発環境（構築済み・再構築時のみ参照）

> 現在の Mac では構築済みです。機材を変えるときだけ見てください。

1. **Xcode 26** を App Store からインストール（初回起動で追加コンポーネント許可）
2. **JDK 17**（KMP 共有モジュール用）: `brew install temurin@17`
   - Xcode の Run Script は `~/.zshrc` を読まないため、スクリプト内で
     `export JAVA_HOME=$(/usr/libexec/java_home -v 17)` が必要です
3. リポジトリを clone し、ルートで一度:
   ```bash
   ./gradlew :shared:embedAndSignAppleFrameworkForXcode || true
   ./gradlew :shared:compileKotlinIosArm64   # K/N ツールチェーン初回DL
   ```
4. Xcode プロジェクト（ColorHunt）を開き、以下を確認:
   - Minimum Deployments = **iOS 16.0**
   - Supported Destinations = **iPhone のみ**
   - Run Script（shared フレームワーク埋め込み）のパスが新環境の実パスか
   - Framework Search Paths が `shared/build/xcode-frameworks/...` を指すか
   - Info.plist: `NSPhotoLibraryUsageDescription` / `NSPhotoLibraryAddUsageDescription`
     / `NSCameraUsageDescription`（ハントカメラ）
   - Copy Bundle Resources には `Assets.xcassets` / 4つの `Localizable.strings` /
     `PrivacyInfo.xcprivacy` **のみ**（リポジトリ全体を追加すると
     `Multiple commands produce` で失敗します）
   - Localizations: en / ja / ko / zh-Hans が登録済みか

> ⚠️ **`.xcodeproj` はこのリポジトリに含まれていません。** 署名設定・Info.plist の
> 権限文言・アイコンの割り当ては Mac 上にしか存在しないため、Mac が壊れると
> 失われます。v1.0 提出後に、`.xcodeproj` をリポジトリへコミットすることを
> 強くおすすめします。

### 3.4 メモリ実測（提出前の必須ゲート）

#### なぜ測る必要があるのか

ハントに取り込んだ写真は、**全てデコード済みの `UIImage` としてメモリに常駐**します
（`AppState.photos`）。1枚あたり最大 1200×1200×4バイト ≒ **5.5MB**。200枚なら
**900MB 前後**に達します。

iOS はアプリのメモリ使用量が端末ごとの上限を超えると、**警告なしで強制終了**します
（jetsam）。クラッシュログには何も残らず、ユーザーからは「突然落ちるアプリ」に
見えます。上限の目安:

| 端末 | 搭載RAM | アプリの上限（目安） | 200枚の見込み |
|---|---|---|---|
| iPhone 8 / SE(2nd) | 2〜3GB | 約 1.2〜1.4GB | **危険** |
| iPhone 11 / 12 | 4GB | 約 2GB | 注意 |
| iPhone 15 / 17 Pro | 8GB | 約 3GB〜 | 余裕 |

**最新機だけで確認しても意味がありません。** 対応下限を iOS 16 にしている以上、
2〜3GB 機で落ちないことを確認する必要があります。

#### 準備（ここを間違えると測定値が無意味になります）

1. **実機で測る。シミュレータは不可**
   シミュレータは Mac の RAM を使うため上限が事実上無く、jetsam も起きません。
   数百MB 超過していても平然と動いてしまいます。

2. **Release ビルドで測る**
   Xcode → Product → Scheme → **Edit Scheme…** → 左の **Run** → Info タブ →
   **Build Configuration** を `Debug` から **`Release`** に変更。
   Debug ビルドは最適化が無効で実際より多くメモリを使うため、Debug のまま測ると
   不必要に厳しい判定になります。
   > 測り終えたら **必ず `Debug` に戻してください**。忘れるとブレークポイントが
   > 効かなくなり、後で原因不明の「デバッグできない」状態に悩むことになります。

3. **一番古い実機を使う**
   手元に 2〜3GB 機が無い場合の代替は「#### 古い実機が無い場合」を参照。

4. **クリーンな状態から始める**
   端末からアプリを削除 → 再インストール。前回のハントデータが残っていると
   取り込み枚数が変わり、比較できません。

#### 測定手順

**A. Memory Gauge で全体像を見る（まずこれ）**

1. Xcode から実機に Run（Release 構成）
2. Xcode 左ペインの **Debug navigator**（⌘7）→ **Memory** をクリック
3. 右側に実時間のグラフと現在値が出ます。ここの数値が **footprint**（＝iOS が
   jetsam の判定に使う値）です
4. アプリを操作しながら、下の順で**各段階の数値を記録**します

| # | 操作 | 記録する値 | 目安 |
|---|---|---|---|
| 1 | 起動直後・ハント空 | ベースライン | 50〜80MB |
| 2 | 「自動で仕分け」→ 200枚取り込み完了 | **取込ピーク** | ここが最大になりがち |
| 3 | ハント画面を一番下までスクロール | 全サムネ描画後 | |
| 4 | 20枚選択 → コラージュ画面へ | | |
| 5 | Pro テンプレで **2160px 書き出し** | **書き出しピーク** | 一時的に跳ねます |
| 6 | 書き出し後、10秒待つ | 落ち着いた値 | 2 と同程度に戻るはず |

5. **さらに重要: アプリを一度終了して測り直す**
   アプリスイッチャーから完全に終了 → 再起動 → **ハント画面を最下部まで
   スクロール** → もう一度 Memory Gauge を確認。
   > 再起動直後は写真がディスクから遅延読み込みされるため、**スクロールするまで
   > 数値が低く出ます**。ここを飛ばすと「大丈夫だった」と誤判定します。
   > スクロールし切った後の値が、実際の常用時の値です。

**B. 上限までの残量を数値で見る（確実な方法）**

Memory Gauge は「今いくつ使っているか」は分かりますが「あと何MB で落ちるか」は
分かりません。それを直接測るのが `os_proc_available_memory()` です。

`ColorHuntApp.swift` の `AppDelegate` に、以下を**一時的に**貼ります
（測定用。**測り終えたら消してください**。v1.0 は凍結済みのためコミットしない
運用です）。手順の詳細と、SwiftUI 側に置いてはいけない理由は
`OWNER_TASKS.md` §C-2 にあります。

```swift
func application(_ application: UIApplication,
                 didFinishLaunchingWithOptions options: [UIApplication.LaunchOptionsKey: Any]? = nil) -> Bool {
    let timer = Timer(timeInterval: 2, repeats: true) { _ in
        let remain = Double(os_proc_available_memory()) / 1_048_576
        print(String(format: "🧠 残り %.0f MB", remain))
    }
    // .common: 既定モードだとスクロール追跡中に止まり、メモリが最も厳しい
    // 「一覧を最下部までスクロール」の最中がまさに測れなくなる。
    RunLoop.main.add(timer, forMode: .common)
    return true
}
```

ファイル冒頭に `import os` が必要です。Xcode のコンソールに 2秒ごとに
「あと何MB でアプリが強制終了されるか」が出ます。

**この残量が 200MB を切ったら、その端末では落ちる寸前です。**

#### 判定

**B の「残量」** を基準に判断してください（A の絶対値より信頼できます）。
最も厳しい段階（通常は 200枚取込直後、または 2160px 書き出し中）の値で判定します。

| 残量 | 判定 | 対応 |
|---|---|---|
| **500MB 以上** | 合格 | そのまま v1.0 をリリース |
| 250〜500MB | 要注意 | リリース可。ただし v1.1 でサムネイル分離を最優先 |
| **250MB 未満** | **不合格** | **リリース前に改修が必要**（下記） |

Memory Gauge の絶対値だけで見る場合の代替基準は **700MB**。これを超えたら
2〜3GB 機で落ちると考えてください。

#### 不合格だった場合の改修（半日程度）

サムネイルと原寸を分離します。方針:

1. `HuntPhoto` に `thumbnail: UIImage`（長辺 300px 程度）を持たせ、**一覧・グリッド・
   マップのピンはサムネイルだけを描画**する
2. 原寸は常駐させず、`Documents/HuntStore/` の JPEG から**必要な時だけ読む**
   （トリミング編集を開いた時・コラージュ書き出し時）
3. 読んだ原寸は `NSCache` に入れ、メモリ警告で自動的に捨てさせる

これで常駐分が 200枚 × 約0.35MB ≒ **70MB** まで下がります。

#### 古い実機が無い場合

2〜3GB 機が手元に無い場合、次のいずれかで代替できます。

- **Instruments の Allocations で絶対値を確認する**
  Xcode → Product → **Profile**（⌘I）→ **Allocations** → Record。
  実機なら「Persistent Bytes」でどのオブジェクトが常駐しているか内訳が見えます。
  `UIImage` / `CGImage` の合計が支配的なら想定どおりです。
- **上の判定表の 700MB 基準で、手持ちの最新機で測る**
  footprint はどの端末でもほぼ同じなので、**使用量は最新機で測っても同じ値**です。
  変わるのは「上限」だけ。つまり最新機で 700MB を超えていたら、古い端末では
  落ちると判断できます。**この方法で十分に判定できます。**
- **メルカリ等で iPhone 8 / SE(2nd) を調達する**（1万円前後）
  今後も長く必要になるので、本気で世界展開するなら持っておく価値はあります。

> 実測値は下の表に記録しておくと、次バージョンとの比較ができます。
>
> | 日付 | 端末 | 起動時の残量 | 残量(最小) | 消費量 | 判定 |
> |---|---|---|---|---|---|
> | 2026-08-02 | iPhone 17 Pro | 3329 MB | 2611 MB | **718 MB** | 要改修（1枚3.59MB×200） |
> | 2026-08-02 | iPhone 17 Pro | 3348 MB | 3144 MB | **204 MB** | **合格**（サムネイル分離後・1枚1.02MB） |
>
> 2行目が現行です。footprint に直すと約218MBで、§3.4 の絶対値基準700MBを大きく
> 下回るため、**iPhone 8（上限約1.4GB）でも1.1GB以上の余裕**があります。最小値は
> 自動仕分けの取り込み中に出ました。

### 価格を ¥500 にした理由（2026-08-02 調査）

競合の実勢はこうです。

| アプリ | 形態 | 日本価格 |
|---|---|---|
| Dazz（フィルムカメラ） | フィルター単体 | **¥250** |
| Dazz | 年額 / 買い切り | ¥480 / ¥1,220〜2,200 |
| CollagePlus | 月額 / 買い切り | ¥700 / ¥10,000 |

この層は**サブスク主軸で、買い切りは「高めの逃げ道」**として置かれています。
Dazz の単体¥250が「迷わず押せる」価格帯を示しています。

- **¥500 はワンコインの内側。** 日本の App Store では ¥500 に明確な段差があり、
  超えると一度考えます。買いやすさを優先するなら、その境界で最も高い値。
- **¥250〜300 は避ける。** レビュー0件・無名開発者の新規アプリでは品質シグナル
  を下げます。画面の作り込みを自ら値引く必要はありません。
- **買い切りは後から値上げできる**（既存購入者は影響なし）。まず ¥500 で出し、
  売れるなら上げる。逆順は初期購入者に不利なので避けます。
- **ローンチ割引はしない。** 流入ゼロの段階では価格は制約になっていません。
  ボトルネックは発見されるかどうかです。将来バズったとき ¥300 へ一時的に
  下げるカードは残ります（**アプリ内課金の価格変更は審査不要**）。

収支の目安（手数料15%を引いた1本 ¥425、転換率はインストールの1〜3%）:

| インストール | 購入見込み | 手取り |
|---|---|---|
| 1,000 | 10〜30本 | ¥4,000〜13,000 |
| 5,000 | 50〜150本 | ¥21,000〜64,000 |

### リワード広告の検討結果（2026-08-02）— **v1.0 では入れない**

「広告を見たら Pro テンプレを一定期間使える」案を評価した。方向性は写真アプリで
実績のあるモデルだが、v1.0 には入れず v1.1 以降にデータを見てから判断する。

**理由1: プライバシー対応がほぼ全部ひっくり返る。** AdMob を入れると
デバイスID・広告データ・使用状況・診断データを「収集する」と申告することになり、
IDFA を使うなら ATT の許可ダイアログも要る。結果として:

- 商品ページの**「データを収集していません」バッジを失う**
- `PrivacyInfo.xcprivacy` を書き換え（tracking=true・収集データ・トラッキングドメイン）
- `site/privacy.html` を全面改訂（「広告SDK…組み込まれていません」が嘘になる）
- 説明文4言語から「広告も、アカウント登録も、利用状況の収集もありません。」を削除
- `site/index.html` の FAQ も修正

**これは後から戻せない。** 先にきれいな状態で出し、必要になったときに意識的に
手放すほうが順序として正しい。

**理由2: ユーザーがゼロの今、広告収益もゼロ。** 判断を先送りするコストがない。

**理由3: カニバリの線引きに実データが要る。** eCPM を仮に ¥1,000（1視聴≒¥1）と
置くと、Pro 1本の手取り ¥425 に相当するのは**約425回の視聴**。つまり「買った
はずの1人」が広告に流れると、穴を埋めるのに数百回要る。広告は「買わない人から
少し貰う」設計でなければならず、その線は Pro の実転換率が分かるまで引けない。

**入れる場合の設計指針**（v1.1 で判断するとき用）:

| | |
|---|---|
| ❌ 期間制（24時間など） | 週1回しか使わない層は**永久に課金しない**。完全な代替品になる |
| ✅ 回数制（1視聴＝1作品） | 毎回30秒待つ手間が積み上がり「買ったほうが早い」圧力が働く |

**透かし削除だけは絶対に広告で開けない。** 透かしは無料ユーザーが広告塔になる
仕組み（下記「グロースの核」）で、広告で外せると拡散力と Pro の芯を同時に失う。
広告で開けてよいのは **Pro テンプレート7種だけ**。

### 先に試すべき継続収益: テンプレートパックの追加課金

プライバシー表示を壊さずに継続収益を作れる。Dazz が単体フィルターを ¥250 で
売っているのがこのモデル（§6 の価格調査）。季節ごとに新パック（桜・夏祭り・
紅葉・クリスマス）を ¥250〜300 で出す。

- プライバシー表示は無傷、SDK 依存もゼロ
- 実装は既存のテンプレ機構の拡張だけ
- 「今日の色×季節イベント」で無料側を話題化する計画と噛み合う

**失うものが無いので、広告よりこちらを先に試す。**

Xcode の StoreKit エディタがハイフンを弾くため。Bundle ID 自体は `com.yk-dev.ColorHunt` のまま）
にしてあります（`AppState.swift` の `proID`）。

- Step 4 で App Store Connect に登録するときは、**この文字列を1文字違わず**
  入力してください。違うと購入画面が「製品情報を読み込めませんでした」になります
- **一度作成したIDは削除も改名もできません。**登録時に必ず見比べること

**0-2. iPhone 専用に絞る（15分）**

iPad を対象に含めると **iPad用スクリーンショットが必須**になり、iPadでの表示崩れが
リジェクト理由にもなります。本アプリは縦持ちiPhone前提の設計です。

- Xcode → TARGETS → General → **Supported Destinations** から
  iPad / Apple Vision を削除し、**iPhone だけ**にする

**0-3. 輸出コンプライアンスの申告を省略する（5分）**

未設定だと**アップロードのたびに暗号化の質問**が出ます。本アプリは独自暗号を
使っていないため、Info に以下を追加すれば以後スキップされます。

- キー: `ITSAppUsesNonExemptEncryption` / 型: Boolean / 値: **NO**

**0-4. バージョン番号（5分）**

- General → Identity → **Version = 1.0.0** / **Build = 1**
- 以後アップロードのたびに Build を +1（1.0.0 のまま Build だけ上げる）

### Step 1. 承認メールが届いたら（30分）

1. Xcode → Settings → **Accounts** → 自分のApple IDを選択 → **Team** に有料の
   チーム（個人名）が出ているか確認。出ない場合は「Download Manual Profiles」
2. TARGETS → **Signing & Capabilities** → Team を**有料チーム**に変更
   （無料のPersonal Teamのままだと提出できません）
3. **Automatically manage signing** にチェック
4. ビルド → 実機インストールできることを確認

> ここで Bundle ID (`com.yk-dev.ColorHunt`) は自動で Apple に登録されます。
> 手動登録は不要です。

---

### Step 2. 有料App契約を結ぶ（30分＋審査数日）★見落とし注意

**この契約が済むまで、課金は一切動かず、アプリも販売できません。**
Sandboxテストすら失敗します。承認されたら**真っ先に**着手してください。

App Store Connect → **契約/税金/口座情報**（Agreements, Tax, and Banking）

1. **有料App契約**（Paid Apps）の「同意する」
2. **銀行口座**を登録（振込先。屋号なしの個人口座で可）
3. **税務フォーム**を提出
   - 日本の居住者は **W-8BEN**（米国以外の個人）を提出します
   - 米国源泉徴収の軽減（日米租税条約）を受けるため、マイナンバーの入力欄があります

状態が「**アクティブ**」になるまで数日かかることがあります。ここが全体の
クリティカルパスになりやすいので、他の作業と並行して進めてください。

| 項目 | 入力 |
|---|---|
| プラットフォーム | iOS |
| 名前 | ColorHunt（※App Store上で一意。取られていたら別名に） |

### Step 4. 課金アイテムを作成してテスト（1〜2時間）

**4-1. 商品を作る**

アプリのページ → **App内課金**（In-App Purchases）→ **＋**

| 項目 | 入力 |
|---|---|
| タイプ | **非消耗型**（Non-Consumable）※買い切り |
| 参照名 | ColorHunt Pro（管理用・非公開） |
| 製品ID | **Step 0-1 で確定させた文字列**（コードと完全一致させる） |
| 価格 | **¥500**（US$2.99 相当。根拠は §6） |
| 表示名 | ColorHunt Pro |
| 説明 | 透かしを削除し、Pro限定テンプレート7種と2160pxの高画質書き出しが使えます |
| 審査用スクリーンショット | ペイウォール画面のスクショ（**必須**）。撮り方は `OWNER_TASKS.md` §E |

**4-2. Sandboxテスターを作る**

ユーザーとアクセス → **Sandboxテスター** → ＋
（**普段使っていないメールアドレス**で作成。実際のApple IDとは別物です）

**4-3. 実機で購入テスト**

1. iPhone の 設定 → App Store → **Sandboxアカウント** に上で作ったテスターでサインイン
2. アプリを起動 → ペイウォール → 購入
3. 確認すること:
   - 価格が正しく表示される（表示されない場合は製品IDの不一致か Step 2 未完了）
   - 購入後に透かしが消え、Proテンプレの王冠が外れる
   - アプリを削除→再インストール→**購入を復元**で戻る

### Step 5. ストア掲載情報を埋める（半日）

アプリのページの各項目を埋めます。

- **スクリーンショット**: Step 0-5 の6枚
- **プロモーションテキスト / 説明 / キーワード**: `docs/STORE_LISTING.md` を流用
- **サポートURL / プライバシーポリシーURL**: Step 0-6 のもの
- **年齢制限指定**: 質問に答える（本アプリは全て「なし」→ 4+ になります）
- **App のプライバシー**: 「データを収集していません」を選択
  - 写真もカメラも**端末内でのみ処理**し外部送信しないため、これが正解です
  - これは強い訴求点なので、説明文にも一言入れると効果的です

---

### Step 6. アップロードして TestFlight で配布（半日＋テスト期間）

1. Xcode 上部の実行先を **Any iOS Device (arm64)** に変更
2. **Product → Archive**（数分かかります）
3. Organizer が開く → **Distribute App** → **App Store Connect** → **Upload**
4. 15〜30分ほどで App Store Connect の TestFlight に現れます
5. **内部テスト**: 自分を追加 → 審査なしで即インストール可
6. **外部テスト**: 知人のメールを招待（初回のみ簡易な審査あり・最大1万人）

> 知人には TestFlight アプリをインストールしてもらい、届いた招待リンクから
> 入れてもらいます。フィードバックはスクショ付きで TestFlight から届きます。

---

### Step 7. 審査に提出（30分＋審査1〜3日）

1. §7 のリリース直前チェックを全て確認
2. アプリのページ → ビルドを選択
3. **App Review に関する情報**:
   - 連絡先（自分の名前・電話・メール）
   - **メモ**: 審査員向けの補足。以下をそのまま書けば十分です
     > 本アプリは写真の色を判定して整理・コラージュするアプリです。
     > すべての処理は端末内で完結し、データの外部送信はありません。
     > カメラと写真ライブラリの権限は、色の判定と作成した画像の保存に使用します。
     > App内課金（ColorHunt Pro）は、コラージュ画面右上のバナーから確認できます。
4. **バージョンのリリース**: 「手動でリリース」を推奨
   （審査通過後、自分のタイミングで公開できます）
5. **審査へ提出**

### 詰まりやすいポイント

| 症状 | 原因 |
|---|---|
| 購入画面に価格が出ない | 製品IDの不一致 / **Step 2 の有料App契約が未完了** |
| アップロードできない | Team が無料のPersonal Teamのまま（Step 1-2） |
| iPad用スクショを求められる | Supported Destinations に iPad が残っている（Step 0-2） |
| 毎回暗号化を質問される | `ITSAppUsesNonExemptEncryption` 未設定（Step 0-3） |
| 「同じビルドが既にある」 | Build 番号を上げ忘れ（Step 0-4） |

**リジェクトされた場合**: Apple からの文面をそのまま共有してください。
理由の解釈と、必要なコード修正まで対応します。初回は
「課金の説明不足」「復元ボタンが見つからない」あたりが典型ですが、どちらも
実装済みなので、メモ欄（Step 7-3）で場所を伝えれば通ることがほとんどです。
