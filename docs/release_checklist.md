# リリース判定チェックリスト & 手順書 / Release Readiness Checklist

このドキュメントの **A〜F がすべて ✅ になったらリリース可** とする。
各項目は「手順」と「合格基準(=何が確認できればOKか)」で構成する。CI(緑)は
前提条件だが、**実機で実際の映像・課金・書き出しを1回通すこと**が判定の核心。

> 環境メモ: CI(`.github/workflows/android.yml`)で `testDebugUnitTest` /
> `assembleDebug` / `assembleRelease`(R8) は自動確認済み。以下は**実機/実データ**
> でしか確認できない項目に絞っている。

- 対象ビルド: `assembleRelease`(署名済み)を実機に導入して確認する
- 推奨端末: Xperia 1系(HDR/Log収録が可能な端末)+ 廉価端末1台(トーンマップの
  MediaCodecフォールバック確認用)
- ログ確認: `adb logcat -s VideoExport VideoColor VideoEdit LutBaker`

## A. ビルド・署名(リリース成果物)

| # | 手順 | 合格基準 |
|---|------|----------|
| A1 | リリース署名鍵(keystore)で `assembleRelease` を実行 | 署名済み `.aab`/`.apk` が生成される |
| A2 | 署名済みビルドを実機にインストールして起動 | クラッシュせず一覧が表示される |
| A3 | R8/難読化ビルドで主要画面を一巡(一覧→ビューア→写真編集→動画編集→設定) | ProGuard由来のクラス欠落クラッシュが出ない |

**合格ライン: A1–A3 すべてクラッシュなし。**

## B. 入力変換の実素材検証(今回の新機能・最重要)

各社Log素材を用意し、`動画編集 → カラータブ → 入力` で検証する。素材が用意できない
機材は「近似」表記のとおりスキップ可(ただし C の書き出し経路は必ず1本通す)。

### B1. S-Log3(公式)
- 手順: Sony製 S-Log3/S-Gamut3.Cine 素材を開く → 入力で「Sony S-Log3」を選択
- 合格基準:
  - [ ] 選択すると眠い(フラットな)映像が**コントラスト・彩度の乗った709の見た目**になる
  - [ ] 破綻(色転び・白飛び・黒潰れの急変)がない
  - [ ] 露出±2EV / コントラスト微調整が滑らかに効く

### B2. Apple Log(公式)
- 手順: iPhone Apple Log 素材を開く → 入力で「Apple Log」を選択
- 合格基準: B1と同様に709として自然な見た目になる

### B3. HLG(公式・トーンマップ委譲)
- 手順: HLG 10bit 素材を開く
- 合格基準:
  - [ ] トップバーのバッジが `HLG 10bit` 表示
  - [ ] 入力の自動判定が「HLG(自動)」になっている
  - [ ] **二重トーンマップの兆候(過度に眠い/暗い)が無い** = HDRトーンマップは
        デコーダ側のみで、Log decodeが二重に掛かっていないこと

### B4. 近似系(DJI/各スマホLog)
- 手順: 該当素材があれば選択(無ければグレーランプのサムネイルで概形確認)
- 合格基準:
  - [ ] 選択シートに「近似」ラベルが出ている(誇大表記が無い)
  - [ ] 適用しても破綻せず、概ね持ち上がった黒が戻る方向に働く

### B5. 「なし(709)」= 非回帰の実確認
- 手順: 既存の通常(709)動画で入力=「なし」のまま Faded Film / S-Cinetone 用
  プリセットを適用し、**今回変更前の見た目と比較**
- 合格基準:
  - [ ] 既存プリセットの濃度・色が**以前と変わらない**(バイト一致の実確認)

### B6. 自動判定・記憶・ヒント
- 手順: 素材Aで入力を手動変更 → 別素材Bを開く → 再度素材Aを開く
- 合格基準:
  - [ ] 素材Aの選択が**記憶されている**(per-media memory)
  - [ ] 手動選択後バッジが「手動」表示になる
  - [ ] フラットなLog素材で「Log素材の可能性があります」ヒントが出る(出過ぎない)

**合格ライン: B1–B3(公式)で自然な709化・破綻なし、B5で非回帰、B6で記憶が効く。**

## C. 書き出し全経路(入力変換→LUT→書き出し→SNSセーフ)

- 手順:
  1. 入力変換を選択した素材に、Proではない無料LUT(Clean Contrast等)を適用
  2. `書き出し → SNS標準` で書き出し
  3. `adb logcat -s VideoExport VideoColor` を監視
  4. 生成された `Movies/Lumina/..._LUMINA_*.mp4` を確認
- 合格基準:
  - [ ] 書き出しが完了し通知が「Movies/Lumina に保存しました」になる
  - [ ] `verifySdrBt709` の自己検証が **ok(BT.709/SDR/limited)**。注意トーストが出ない
  - [ ] **プレビューと書き出し結果の色が一致**(入力変換が書き出しにも乗っている)
  - [ ] HDR(HLG)素材でも上記が成立(トーンマップ→LUTの順で709出力)
  - [ ] 廉価端末でOpenGLトーンマップ失敗時、MediaCodecフォールバックで完走する

**合格ライン: SNS標準で自己検証ok・プレビュー一致。HDR素材でも完走。**

## D. 課金(Pro 買い切り)の実機疎通

Play Console で `lumina_pro`(非消費型)を登録し、ライセンステスターで確認する。

- 手順:
  1. Play Console → アプリ内アイテムに `lumina_pro` を登録・有効化
  2. ライセンステスターのアカウントで実機テスト
  3. `設定 → Proを購入` → 購入 → Pro機能(全LUT/.cube取込 等)を確認
  4. アンインストール → 再インストール → 起動 or「購入を復元」
- 合格基準:
  - [ ] 購入完了で全Pro機能が解放される
  - [ ] ProのLUTを当てた動画の**書き出し時にアップセルが出て**、無料LUT+SNSセーフ
        書き出しは**無料で通る**(機能分割の意図どおり)
  - [ ] 再インストール後に購入が復元される(オフライン起動でもキャッシュで維持)
  - [ ] ライセンステスターで実課金が発生しない

**合格ライン: 購入→解放→復元が一巡。無料/Pro境界が仕様どおり。**

## E. 既存機能の回帰(スモーク)

今回の変更は動画カラー周りだが、リリース前に主要フローを一巡する。

- [ ] 一覧: 大量枚数でスクロール滑らか、ピンチ列数変更、日付スクラバー
- [ ] ビューア: 開閉トランジション、下スワイプ閉じ、RAW⇔JPEG切替
- [ ] 写真編集: 調整リアルタイム、フィルタ適用、**別名(非破壊)保存**
- [ ] 動画編集: LUT/強度/調整/トリム/長押しA/B比較
- [ ] 共有・削除(ゴミ箱復元)・アルバム
- [ ] USB/SDカード(SAF)閲覧・取り込み
- [ ] 投稿プレビュー(グリッド/フィード/リール)

**合格ライン: いずれもクラッシュ・明白な破綻なし。**

## リリース可 判定ゲート

> **A・B・C・D・E・F の合格ラインがすべて満たされたとき、リリース可とする。**

特に見落としやすい3点(この機能特有):
1. **C の「プレビューと書き出しの色一致」** — 入力変換が書き出し(WorkManager)側にも
   確実に乗っているか。ここが崩れると「プレビューと違う」不具合になる。
2. **B5 の非回帰** — 既存プリセットの見た目が変わっていないこと。
3. **B4/選択シートの「近似」表記** — 近似系を「純正同等」と誤認させないこと(景表法)。

## 付録: 素材が用意できない場合の代替確認

実機のLog素材が揃わない場合の最低限の代替(ただし B の実映像確認の代わりには
ならない。あくまで補助):

- グレーランプ動画(0→白のグラデーション)を各入力変換で開き、階調が単調に
  持ち上がる/破綻しないことを目視
- `tools/lut_analysis/input_transforms.py` を再実行し、数式が単調・レンジ内で
  あることを確認(S-Log3 18%→0.44付近)

> 注: 近似系(DJI/各スマホLog)は公開カーブが無いため、実素材での最終的な
> 見た目調整は将来のフィードバックで詰める前提。リリース時点では「近似」表記で
> 誠実に提供する。
